Before Anything Else

The honest bit, first

This project is based on a real housing sector role, tracking a live tender and contract book on a UK portfolio management platform. That underlying work is confidential: it belongs to a real employer, involved real bids and real contractors, and none of it can appear here.

So nothing here is real. Every table, every date, every contractor name and every figure in the dashboard below was generated from scratch by a documented Python script, built to reproduce the shape and behaviour of that kind of portfolio: the seasonal surge into financial year end, a funnel that narrows at each stage, win rates that vary by contractor tier, delivery that slips under load. Nothing here is copied, disguised, or approximated from confidential data; it is built independently from public knowledge of how housing tender pipelines behave.

Why this is a feature, not a limitation

Knowing what you cannot show, and being able to reconstruct a credible, internally consistent version of it anyway, is itself part of the job. Anyone can build a dashboard when the data is handed over. Handling the confidentiality boundary well, and still being able to demonstrate the modelling underneath it, is the harder and more useful skill.

Try It Yourself

Try it, no Power BI needed

The dashboard's measure-switcher toggle is the single most useful bit of DAX in this build: one visual, three different numbers, chosen at click time. Here is the same idea in plain JavaScript, redrawing a chart of all 24 months from the real generated tender data, live in your browser.

This mirrors the DAX pattern below: a disconnected selector table drives SWITCH(SELECTEDVALUE(...)) to redraw one visual as three different measures, without duplicating the chart.

DAX Showcase

Three measures that are not as trivial as they look

The measure switcher

Selected Metric =
VAR m =
  SELECTEDVALUE(
    dim_measure_selector[measure_name],
    "Value"
  )
RETURN
  SWITCH(
    m,
    "Value", [Portfolio Value],
    "Count", [Total Bids],
    "Win Rate", [Win Rate]
  )

Why it's not trivial: dim_measure_selector has no relationship to anything. It only exists to be read by SELECTEDVALUE, so a slicer on it changes what a single visual measures rather than which rows it filters. Get the disconnected table wrong and Power BI tries to filter with it instead, and every value silently returns blank.

The league table

Contractor Rank =
RANKX(
  ALL(dim_contractor[contractor_name]),
  [On-Time %],
  ,
  DESC,
  DENSE
)

Why it's not trivial: inside a contractor's own table row, row context has already filtered everything down to that one contractor. ALL() deliberately clears that filter just for the ranking calculation, so every contractor is re-ranked against the full list on every single row, not just compared to itself.

The time intelligence pair

Portfolio Value YoY % =
DIVIDE(
  [Portfolio Value] - [Portfolio Value PY],
  [Portfolio Value PY]
)

Cumulative Portfolio Value =
CALCULATE(
  [Portfolio Value],
  FILTER(
    ALL(dim_date[date_key]),
    dim_date[date_key] <= MAX(dim_date[date_key])
  )
)

Why it's not trivial: both depend on dim_date being marked as an official date table with no gaps. DATEADD and the running total both walk the calendar directly; a single missing day, or a date table built from the fact tables instead of a continuous calendar, breaks both silently.

What's working

  • Tier 1 contractors win nearly three times as often as Tier 3 (49.6% vs. 16.6%) and deliver on time far more reliably (94% vs. 77%): worth consolidating more of the book toward them.
  • Portfolio value grew about 66% year on year (roughly £87M in 2024 to £145M in 2025), a healthier trajectory than headline win rate alone would suggest.
  • North West and South West post the strongest win rates (both 35%), evidence the volume led bid strategy is working best outside London.

What to watch

  • On time delivery sits at 86.7%, just under the 90% target, with 11 contracts currently flagged at risk, concentrated among Tier 2 and Tier 3 contractors.
  • Bid volume spikes hard into the financial year end (January to March) and drops through summer: bid writing resource should flex with it rather than stay flat all year.
  • London and the South East carry the highest average contract value (£1.05M and £0.93M) but the lowest volume and among the lowest win rates (25% and 25%): those regions likely need fewer, larger, more carefully targeted bids rather than the volume approach that works in the north.

Interview Prep

How I'd defend this in an interview

Why synthetic data, not the real portfolio?

The real data is confidential: it belongs to a real employer and involves real bids, real contractors and real commercial figures. Rather than approximate or disguise it, I rebuilt the structure from scratch: same table shapes, same kind of seasonality, same funnel logic, generated by a documented script with a fixed seed. That is also, itself, a skill worth showing: reconstructing a credible dataset from documented rules rather than eyeballing plausible numbers.

Why a gauge and a donut, when the rest of the dashboard avoids them?

Both were deliberate exceptions, not a habit. A gauge is the right chart for exactly one comparison, a single value against a single target, which is precisely what On Time % vs. the 90% target is. A donut works for a small part-to-whole split, which is what portfolio value by status (active, completed, at risk, on hold) is. Everywhere else on the dashboard the comparison is between many categories or over time, where a bar or line tells the truth better than a gauge or donut would.

What was the hardest piece of DAX?

The measure switcher and the RANKX league table, for the same underlying reason: both are about deliberately controlling context. The switcher only works if the selector table stays disconnected, so a slicer on it changes what is measured rather than filtering rows. RANKX only re-ranks every contractor correctly if ALL() clears the row context first; without it, every contractor would rank itself first against nobody.

Why Power BI only this time, no SQL or Excel?

Deliberately. My other portfolio projects already show that range: the crude oil project is SQL led, the Riverside Kitchen project is Python led, and VRIJLOOP runs Excel through SQL into Power BI. This project exists specifically to isolate and prove Power BI and DAX modelling depth on its own, without another tool doing the heavy lifting underneath it.
