Before Anything Else

The honest bit, first

This project is based on a real housing sector role, tracking a live tender and contract book on a UK portfolio management platform. That underlying work is confidential: it belongs to a real employer, involved real bids and real contractors, and none of it can appear here.

So nothing here is real. Every table, every date, every contractor name and every figure in the dashboard below was generated from scratch by a documented Python script, built to reproduce the shape and behaviour of that kind of portfolio: the seasonal surge into financial year end, a funnel that narrows at each stage, win rates that vary by contractor tier, delivery that slips under load. Nothing here is copied, disguised, or approximated from confidential data; it is built independently from public knowledge of how housing tender pipelines behave.

Why this is a feature, not a limitation

Knowing what you cannot show, and being able to reconstruct a credible, internally consistent version of it anyway, is itself part of the job. Anyone can build a dashboard when the data is handed over. Handling the confidentiality boundary well, and still being able to demonstrate the modelling underneath it, is the harder and more useful skill.

SQL Showcase

Three queries that are not as trivial as they look

All three run against the star schema in MySQL and feed both the Excel pivot tables and the Python charts above. Real output from this dataset is shown under each query.

The rolling win rate

SELECT
  d.month_year,
  ROUND(100.0 * SUM(t.is_won)
    / SUM(t.is_decided), 1)
    AS win_rate_pct,
  ROUND(100.0 *
    SUM(SUM(t.is_won)) OVER (
      ORDER BY d.month_year_sort
      ROWS BETWEEN 2 PRECEDING
      AND CURRENT ROW
    ) /
    SUM(SUM(t.is_decided)) OVER (
      ORDER BY d.month_year_sort
      ROWS BETWEEN 2 PRECEDING
      AND CURRENT ROW
    ), 1)
    AS win_rate_3m_rolling_pct
FROM fact_tenders t
JOIN dim_date d
  ON d.date_key = t.identified_date_key
GROUP BY d.month_year, d.month_year_sort
ORDER BY d.month_year_sort;

Why it's not trivial: the window function has to sum the monthly totals over a 3 row frame before dividing, not average three already-divided percentages, which would quietly overweight quiet months. Real output: the rolling win rate reaches 45.1% in December 2025, up from 23.8% in June 2025.

The contractor league table

SELECT
  c.contractor_name,
  c.tier,
  COUNT(*) AS contracts,
  ROUND(100.0 * SUM(f.is_on_time)
    / COUNT(*), 1) AS on_time_pct,
  RANK() OVER (
    ORDER BY SUM(f.is_on_time) * 1.0
      / COUNT(*) DESC
  ) AS on_time_rank
FROM fact_contracts f
JOIN dim_contractor c
  ON c.contractor_id = f.contractor_id
GROUP BY c.contractor_name, c.tier
ORDER BY on_time_rank;

Why it's not trivial: RANK() has to run on the aggregated on-time rate per contractor, not on individual contract rows, so the aggregation and the ranking are two separate steps in the same query. Real output: Northfield Construction ranks first at 96.6%, but the highest ranked Tier 3 contractor, Anchor Point Contracts at 91.3%, still beats three of the six Tier 2 contractors.

The year on year comparison

SELECT
  SUBSTR(f.start_date_key, 1, 4)
    AS start_year,
  ROUND(SUM(f.contract_value)
    / 1000000.0, 1)
    AS portfolio_value_gbp_m,
  ROUND(100.0 * (
    SUM(f.contract_value) -
    LAG(SUM(f.contract_value)) OVER (
      ORDER BY SUBSTR(f.start_date_key, 1, 4)
    )
  ) / LAG(SUM(f.contract_value)) OVER (
    ORDER BY SUBSTR(f.start_date_key, 1, 4)
  ), 1) AS yoy_pct
FROM fact_contracts f
GROUP BY start_year
ORDER BY start_year;

Why it's not trivial: LAG() reaches back to the prior year's total without a self-join, but the first year in the window has no prior row to reach back to, so that year's year-on-year figure is correctly null rather than zero. Real output: portfolio value rises from £87.2M in 2024 to £144.8M in 2025, up 66.0%.

What's working

  • Tier 1 contractors win nearly three times as often as Tier 3 (49.6% vs. 16.6%) and deliver on time far more reliably (94% vs. 77%): worth consolidating more of the book toward them.
  • Portfolio value grew about 66% year on year (roughly £87M in 2024 to £145M in 2025), a healthier trajectory than headline win rate alone would suggest.
  • North West and South West post the strongest win rates (both 35%), evidence the volume led bid strategy is working best outside London.

What to watch

  • On time delivery sits at 86.7%, just under the 90% target, with 11 contracts currently flagged at risk, concentrated among Tier 2 and Tier 3 contractors.
  • Bid volume spikes hard into the financial year end (January to March) and drops through summer: bid writing resource should flex with it rather than stay flat all year.
  • London and the South East carry the highest average contract value (£1.05M and £0.93M) but the lowest volume and among the lowest win rates (25% and 25%): those regions likely need fewer, larger, more carefully targeted bids rather than the volume approach that works in the north.

Interview Prep

How I'd defend this in an interview

Why synthetic data, not the real portfolio?

The real data is confidential: it belongs to a real employer and involves real bids, real contractors and real commercial figures. Rather than approximate or disguise it, I rebuilt the structure from scratch: same table shapes, same kind of seasonality, same funnel logic, generated by a documented script with a fixed seed. That is also, itself, a skill worth showing: reconstructing a credible dataset from documented rules rather than eyeballing plausible numbers.

Why split the work across Excel, MySQL and Python instead of one tool?

Because that mirrors how the work actually divides. MySQL does the heavy aggregation once, in one place, using window functions that would be painful to replicate by hand in a spreadsheet: the rolling win rate, the contractor ranking, the year on year comparison. Excel turns that into a workbook a non-technical stakeholder can open, filter and trust without touching a line of code. Python and Matplotlib go deeper, producing the analytical charts that explain why the numbers moved. Each tool is doing the part it is genuinely best at, rather than one tool doing everything by default.

Why compute the rolling win rate and the ranking in SQL rather than in Excel?

Excel can do both with array formulas or PivotTable tricks, but the logic then lives inside one workbook's formulas and has to be rebuilt if anyone wants it anywhere else. Doing it once in MySQL, with a window function, means the same query feeds the Excel PivotTable, the Python charts, and any future front end, without three separate implementations quietly drifting out of sync with each other.

What was the hardest piece of SQL?

The rolling win rate. It is tempting to average three months of already-calculated percentages, but that quietly overweights quiet months with few decided bids. The correct version sums the numerator and the denominator separately over the window frame, then divides once, which meant nesting a window function inside another aggregate rather than writing the obvious first draft.

Why synthetic data generated in Python rather than by hand?

A hand-typed "realistic looking" dataset tends to be internally inconsistent in ways that are hard to spot but easy for a reviewer to poke holes in: totals that do not reconcile, a funnel that does not narrow, values that do not vary sensibly by region. Generating it from a documented script with a fixed seed means every number in this case study, and every chart, can be reproduced and checked by anyone who runs the same three scripts.
